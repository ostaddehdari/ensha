# Ensha v0.26.0 — ENSHA-P1-S06-W01

این ورک، زیرساخت امن پل WordPress در مرحله S06 نقشه اصلی را کامل می‌کند. در این نسخه کلید اتصال دیگر داخل Header ارسال نمی‌شود و هر درخواست با HMAC-SHA256 امضا می‌شود.

## تغییرات اصلی

- امضای درخواست با Method، مسیر داخلی API، Query String، Timestamp، Nonce و SHA-256 بدنه.
- پنجره زمانی پنج‌دقیقه‌ای برای جلوگیری از پذیرش درخواست منقضی.
- ذخیره Nonce به تفکیک مرکز و رد قطعی بازپخش درخواست.
- الزام `X-Ensha-Idempotency-Key` برای همه درخواست‌های تغییردهنده.
- ذخیره و بازپخش پاسخ درخواست تکراری بدون ساخت نوبت یا مراجع دوباره.
- رد استفاده یک کلید Idempotency برای بدنه‌ای متفاوت.
- امضای خودکار درخواست‌ها در افزونه WordPress، حذف ارسال مستقیم `X-Ensha-Key` و عدم بازتاب کلید در HTML تنظیمات.
- استقلال کامل داده‌های Nonce و Idempotency بین مراکز.

## قرارداد امضا

رشته Canonical از شش خط تشکیل می‌شود:

```text
METHOD
/api/v1/centres/{centre}/path
query-string مرتب‌شده بر اساس کلیدها با RFC3986
unix-timestamp
nonce
sha256(raw-body)
```

امضا برابر `HMAC-SHA256(canonical, api_key)` است و به‌صورت Hex در Header `X-Ensha-Signature` ارسال می‌شود. کلید API در Laravel به‌صورت رمزگذاری‌شده نگهداری می‌شود و افزونه WordPress آن را در HTML صفحه تنظیمات بازتاب نمی‌دهد.

برای متدهای امن `GET`، `HEAD` و `OPTIONS`، بدنه در قرارداد امضا همیشه رشته خالی در نظر گرفته می‌شود؛ حتی اگر ابزار تست یا واسط HTTP یک بدنهٔ مصنوعی مانند `[]` بسازد.

## معیار پذیرش

- درخواست بدون امضا، منقضی یا دست‌کاری‌شده با پاسخ 401 رد شود.
- استفاده دوباره از همان Nonce با پاسخ 409 رد شود.
- درخواست POST بدون کلید Idempotency با پاسخ 422 رد شود.
- تکرار رزرو با کلید و بدنه یکسان همان پاسخ نخست را برگرداند و نوبت دوم نسازد.
- استفاده همان کلید برای بدنه متفاوت با پاسخ 409 رد شود.
- آزمون اختصاصی و کل مجموعه Application پاس شوند.

ورک بعدی `ENSHA-P1-S06-W02` است: API پنل مراجع شامل «نوبت‌های من»، لغو، جابه‌جایی و فرم پذیرش. پس از آن ویجت‌های Elementor در S07 روی همین API ساخته می‌شوند.
